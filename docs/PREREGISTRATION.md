# Head-to-head on MetaTime: what was declared, and when

This file holds the declarations and reporting notes of the head-to-head, word for word as
they were written. The rules came first: the task list, the question, the metrics, the
primary estimator, the controls and the success criterion were committed and pushed before
any estimate of ours existed on the benchmark, and every later addition was committed and
pushed before it was run. The results are in [`METATIME.md`](METATIME.md).

**Where the text comes from.** The first nine entries below were first written as dated notes in
section 7 of the pre-registration file of this project's earlier coding-task study, at
`docs/PREREGISTRATION.md` in the commits listed in the table. That study is no longer in
this repository's tree. It stays in the git history up to commit
[`aa450e4`](https://github.com/isHeSatoshi/anthropochrony/tree/aa450e4c6a2fd6094b800d75fe26ad4216888796),
where the full file can be read, and its models and data stay on the Hugging Face Hub.
Names and paths inside those entries ("the main study", `H1-H6`, `M1`,
`src/anthropochrony/...`) describe the repository as it was when the entry was written.

## Entries, word for word

- 2026-11-14, exploratory head-to-head on a public benchmark (local GPU only; not part of H1-H6). Written and committed **before any estimate of ours on the benchmark was produced**; at this point only timing runs of the base model had started, and no estimate had been asked for. Benchmark: the 68 single-turn tasks of the public MetaTime artifact (`anonymous.4open.science/r/Time-Estimation-B286`, snapshot 8 Oct 2026; the Garikaparthi 2026 suite), with the artifact's prospective question verbatim and the task's short description as the only task text. We do not redistribute the tasks. Target: the model's own wall-clock time for the task prompt on this machine (RTX 4060 Ti, PyTorch/transformers bf16, one request at a time, 2,048-token cap, model-card sampling), median of 5 runs. Training data: the model's own median response length (3 runs) on a pool of public instruction prompts (Dolly-15k, CodeAlpaca-20k, no_robots, GSM8K, 100 of our own `train` coding tasks; pinned revisions in `scripts/metatime/build_pool.py`), from which every prompt with TF-IDF cosine >= 0.25 to any benchmark prompt or description was removed (21 of 1,544). No benchmark task, response or duration is used for training, model selection or calibration. **Primary estimator:** a new LoRA (`G1`, seed 0; M1 recipe: r16, alpha 32, lr 2e-4, 2 epochs) answering the benchmark question with the stated speed of this deployment in the system prompt (held-out phrasing `sc07`), scored on the time it states, parsed by the benchmark's own parser, against the runs of the same fine-tuned model. **Metrics:** the benchmark's (median estimate/actual ratio, median absolute log error, Pearson r on log durations), plus within-2x and MAE. **Comparison:** the artifact's per-task prospective estimates of GPT-5.5 and Claude Opus 4.8 on the same 68 tasks (each model against its own measured time), with a paired task bootstrap (5,000 draws) of the difference in median absolute log error; and the best trained Qwen3-8B numbers of the paper's Table 22 (before generating: MAE 24.04 s, r 0.44). **Declared success criterion:** lower median absolute log error than both frontier models with the paired 95% interval excluding zero; the correlation is reported whether or not it is higher. **Secondary, all reported:** base-model executor, full-prompt view, the token reading (stated tokens through the speed formula), the paper's question wording, the untrained base model with and without the stated speed, pool-only static baselines (constant, text regressor), and more seeds if time allows. The comparison is across models and deployments by design (each model predicts its own time), so it shows which system knows its own time better, not which model is more capable.
- 2026-11-14, amendment to the head-to-head above, written and committed **before label generation, training or any estimate**. (1) The stated speed is rounded to two significant digits, as every stated speed in training is. (2) Training adds replay examples: each pool prompt alone, with the first 128 tokens of the base model's own response (first label run) as the target. Reason: the primary score is against runs of the fine-tuned model, so the adapter must leave ordinary task behaviour, and with it the response lengths the labels were measured on, unchanged. Whether response length drifts is checked on held-out pool prompts before any benchmark run of the fine-tuned model. (3) A linear probe on the untrained model's hidden state (layer and penalty chosen on held-out pool prompts) joins the secondary baselines. (4) Added while the training labels were still being generated, before training: two more secondary rows. A frozen sentence-encoder regressor (the project's B2 family) joins the pool-only baselines, and the same adapter is also read as the median of 16 answers sampled at temperature 1, with the share of measured times inside the 10th-90th percentile range of those answers. The primary estimator stays the single greedy answer. (5) Added while the adapter was still training, before any estimate of ours on the benchmark: one more secondary row. The untrained model with the stated speed is also shown five measured examples from the training pool as earlier turns: the benchmark question about the training prompts at the 50th, 10th, 90th, 30th and 70th percentile of measured response length (in that order), each answered as the training data would answer at the stated speed. It tests whether training is needed or measured examples in the prompt are enough. (6) Added at the same time, also before any estimate of ours on the benchmark: a stated-speed sweep. The primary question is also put to `G1` and to the untrained model with four of the project's evaluation speed cards stated in place of the measured one (`extrap-low` 1.5/10, `seen-cpu` 8/60, `heldout-190` 190/19,000 and `seen-dc` 400/40,000 tokens per second writing/reading). Each answer is scored against the same executor's measured runs replayed at the stated speed (measured prompt and response tokens through the speed formula, which matched measured wall time on this machine to 0.011 median absolute log error in the base model's first timing pass). It tests whether the stated time follows the stated hardware; those targets are computed, not measured on such machines. (7) Also declared before any estimate of ours on the benchmark, to run if time allows: seeds 1 and 2 of the same recipe, and a training-size curve (seeded samples of 150 and 450 of the 1,353 training prompts, seed 0). These extra adapters are scored against the untrained model's runs, with the same length-drift check on held-out pool prompts, because timing every adapter's own runs would not fit in the time left.
- 2026-11-15, results of the head-to-head declared above (reporting note; no rule, estimator or criterion was changed after the first estimate). All 68 tasks were run and all 68 primary answers parsed. Primary (`G1` seed 0, stated time, its own runs, median of 5): median estimate/actual 0.74x, median absolute log error 0.377 (95% CI 0.32 to 0.45), Pearson r on log durations 0.78, 79% within 2x, MAE 6.6 s. Published GPT-5.5: 3.47x, 1.24, r 0.55. Published Claude Opus 4.8: 2.87x, 1.06, r 0.81. Paired differences in median absolute log error: -0.87 (95% CI -1.06 to -0.70) and -0.68 (-0.79 to -0.51), so **the declared success criterion is met**. The correlation is not higher than Claude Opus 4.8's. Every declared secondary row is in `results/metatime.json` and `docs/METATIME.md`, including the negative ones: without the stated speed `G1` scores 1.77, worse than both frontier models; five in-prompt examples leave the untrained model at 1.29; the 10th-90th percentile range of 16 samples covers 50% of measured times; a linear probe on the untrained model, read just before it answers the full prompt, scores 0.36 and so matches `G1` shown the full prompt (0.32 on its own runs, 0.33 on the untrained model's runs). Held-out pool check, done before the fine-tuned model saw a benchmark task: 0.38 from the description, 0.32 from the full prompt, response-length drift +0.5%. Both models have 5 timed runs per task; `G1`'s benchmark estimates were produced before its own timed runs. Added after the results were seen, and marked as context where reported because they use benchmark outcomes or are descriptive: the leave-one-out own-median constant and rescaled rows, the per-category table, the Spearman and pair-ordering figures, the artifact's after-completion estimates, and the per-task change of each estimate with the stated speed. Seeds 1 and 2 and the 150- and 450-prompt adapters (item 7) were still training when this note was written. No paid compute was used for this arm.
- 2026-11-15, one post-hoc addition to the head-to-head, written and pushed before it was computed (it was not declared before the benchmark estimates, so it is exploratory). The sampled range under-covers, so we also report a split-conformal range that uses no benchmark outcome: the score is the absolute log ratio of `G1`'s stated time to the target on the 170 held-out pool prompts; `q` is its ceil((n + 1) x 0.8)-th smallest value; the range for a benchmark task is the stated time divided and multiplied by `e^q`. Reported for the description and the full-prompt question: `q`, the factor `e^q`, and the share of the 68 measured times inside the range, whatever it turns out to be. Nothing is tuned on the benchmark.
- 2026-11-15, result of the post-hoc range declared in the previous entry, computed after that entry was pushed and reported as declared. Calibration on the 170 held-out pool prompts (rank 137): from the description `q` = 0.92, a factor of 2.52, and 93% of the 68 measured times are inside the range (93% against the untrained model's runs as well); from the full prompt `q` = 0.63, a factor of 1.88, and 85% are inside (82% against the untrained model's runs). The target was 80%, so the description range over-covers on this suite. First extra adapter of item 7 (150 training prompts, against the untrained model's runs): stated time 2.95, stated tokens through the speed formula 0.64 (r 0.45); none of its 68 stated times agrees with its own token counts within 10%. The agreement count was added to the adapter table after seeing those answers.
- 2026-11-15, second post-hoc addition to the head-to-head, written and pushed before the adapter it describes was trained (exploratory; the primary estimator and the declared success criterion do not change). The primary estimator needs the deployment's speed in its prompt, while the frontier models were asked without one. To test that condition for our model, one more adapter (`G1-fixed`: same recipe, pool, labels and seed 0 as `G1`) is trained with no system prompt and with every training answer computed at one fixed speed, the untrained model's measured speed on this GPU as stated in its benchmark rows (34 tokens a second writing, 5,700 reading). It is asked the artifact's question exactly as the frontier models were (task description, no system prompt, no speed), and also with the full prompt in place of the description. It is scored on the time it states, read by the benchmark's parser, against the untrained model's 5 timed runs, as the other extra adapters are, with the same response-length drift check on held-out pool prompts, the same paired comparison against the two frontier models, and the same pool-calibrated range. Reported whatever it scores. Limit known in advance: an adapter trained this way is tied to one machine's speed and cannot follow a change of hardware. Order of the remaining local GPU jobs: this adapter first, then seeds 1 and 2 of item 7 (the first attempt at seed 1 is stopped at its start and retrained from scratch).

Pool-calibrated range: factor 2.88 with 99% of measured times inside (description), factor 1.84 with 79% inside (full prompt). Addition, declared now and run after seed 1: because those rows use the untrained model's runs, `G1-fixed` is also timed itself on the 68 tasks with the adapter merged into the weights (as a deployment would serve it; unmerged LoRA layers slow decoding by about 12% on this GPU), 3 runs per task because of the time left, and the same answers are scored against the median of those runs. Whatever that gives is reported next to the row above. Seed 2 follows if time allows. The 450-prompt adapter of item 7 scored 0.41 (r 0.64, 78% within 2x) against the untrained model's runs.

- 2026-11-15, third post-hoc addition to the head-to-head, written and pushed before any of the steps it describes was run on the full pool (exploratory; the primary estimator, `G1` seed 0, and the declared success criterion do not change). Why: the hackathon track this project is entered in asks that the work chain the track's libraries (CuratorKIT, AlignTune, AuditKIT) into one pipeline, and `G1` and its variants were trained by our own PyTorch/PEFT loop and scored only by our own scripts. One more adapter, `G1-kit`, is built end to end by that pipeline. (1) CuratorKIT 0.1.23 (`scripts/metatime/curate.py`) gates the 1,353 training-split pool prompts; the 170 held-out pool prompts are untouched. Each sample is the prompt, the model's own first measured response and its three measured response lengths. CuratorKIT runs its schema gate, exact and MinHash near-duplicate removal (threshold 0.7, seed 20261115) and its secrets gate, with no text rewritten; one rule of ours runs as its preprocessing hook and drops a prompt when any of its measured runs stopped at the 2,048-token generation cap (the label is then a lower bound) or its measured response is empty. Counts before and after, by stage and by reason, are reported. (2) AlignTune 0.1.32's SFT trainer (`scripts/metatime/train_aligntune.py`; TRL 1.7.1 backend, PEFT LoRA r=16, alpha 32, dropout 0.05 on all seven attention and MLP projections, learning rate 2e-4 with cosine decay and 5% warm-up, weight decay 0.01, 2 epochs, batch 1 with 16 accumulation steps, bf16, gradient checkpointing, seed 0, loss on the answer tokens only) trains on the estimate examples that `train.py` builds for `G1`, with the same seeds per prompt, restricted to the prompts CuratorKIT passed, plus one replay example per prompt holding the model's complete measured response (sequence limit 1,536 tokens; longer ones are cut there). Differences to `G1`, named in advance: the curated subset, complete instead of 128-token replay responses, and TRL's batching instead of ours. (3) Estimates as for the other seeds: `estimate.py` with `card_description` and `card_full_prompt`, the stated speed measured on this GPU with the adapter off, the held-out pool check and the response-length drift check. Scored by `score.py` against the untrained model's five timed runs with the same metrics, and reported whatever the result. (4) AuditKIT 1.1.6 (`scripts/metatime/audit.py`) evaluates the untrained model told its speed and `G1-kit` on the 68 tasks with three scorers (absolute natural-log error of the time read by the benchmark's own parser against the untrained model's median run, within 2x, parsed), compares them with AuditKIT's paired bootstrap, and checks that its greedy answers equal the ones `estimate.py` wrote. Its lm-eval engine measures capability before and after: `arc_easy` and `arc_challenge`, zero-shot, the untrained model against the model with `G1-kit` switched on. Local GPU only, no paid compute.
- 2026-11-15, addition to item (4) of the previous entry, written and pushed before AuditKIT is run (descriptive; no rule, estimator or criterion changes). `audit.py` also records, for each arm, the prompt and answer token counts and the wall time of its 68 greedy answers. The write-up turns them into a cost per 1,000 estimates: for our model, the measured wall time scaled to 1,000 answers times a public on-demand hourly price for this GPU; for the frontier models, 1,000 times the same prompt and answer token counts times their list prices per million tokens. The second number undercounts their cost, because their own tokenizers, answer lengths and any hidden reasoning tokens are not known, and it is reported as a lower bound.
- 2026-11-15, reporting note for the third post-hoc addition (`G1-kit`) and its cost record (no rule, estimator or criterion changed; the primary estimator remains `G1` seed 0). (1) CuratorKIT passed 1,342 of the 1,353 training prompts (10 dropped by the cap rule, 1 by the secrets gate; deduplication removed none). (2) AlignTune trained for 840 steps in 7,867 s on the RTX 4060 Ti. The run then stopped at the post-training check that the loss covers only answer tokens, after the adapter had been saved: one replay sequence was longer than the 1,536-token limit, the collator had cut it, and the check compared it with the uncut labels. The check was fixed to compare only the part that was kept and passed on a one-step rerun of the same data pipeline (16 sequences); the training summary was rebuilt from the run's log. The adapter was not retrained. (3) Against the untrained model's five timed runs: median absolute log error 0.45 (95% CI 0.37 to 0.59), r 0.75, 76% within 2x; paired difference to GPT-5.5 -0.79 (-1.01 to -0.59, closer on 60 of 68 tasks) and to Claude Opus 4.8 -0.60 (-0.74 to -0.40, 57 of 68); full prompt 0.32; held-out pool prompts 0.41 and 0.36; response-length drift +1.1%. (4) AuditKIT, untrained model against `G1-kit`, both told the speed measured with the adapter off: mean absolute log error 1.78 and 0.50, within 2x 4.4% and 76.5%, paired bootstrap p = 0.001 for both; 68/68 answers parsed and identical to the ones `estimate.py` wrote, in both arms. ARC zero-shot, all questions: ARC-Easy 73.0% and 71.1%, ARC-Challenge 42.2% and 40.2%. One change of analysis, made after the result was seen: AuditKIT's `compare(...).significance()` pairs lm-eval questions by id alone, and ids restart at 0 in each task, so its pooled ARC test paired ARC-Easy questions with ARC-Challenge ones (it reported n 2,376, -2.1 points, p = 0.002). `audit.py` now pairs by task and id with AuditKIT's own bootstrap function, recomputed from the two saved AuditKIT run files: -1.9 points (p = 0.004) on ARC-Easy, -2.0 points (p = 0.04) on ARC-Challenge, -1.9 points (p = 0.001) over all 3,548. Both results are kept in `results/metatime-audit.json`, and both show a small, significant loss. (5) Cost record: 68 answers took 22.57 s for the untrained model and 62.31 s for `G1-kit`, with 35,440 prompt tokens each and 516 and 1,511 answer tokens. Per 1,000 `G1-kit` estimates that is 0.25 GPU-hours, $0.03 to $0.05 at $0.11 to $0.19 an hour; the same token counts at GPT-5.5's and Claude Opus 4.8's list prices ($5 per million prompt tokens; $30 and $25 per million answer tokens) cost $3.27 and $3.16, and the benchmark question alone (5,112 tokens over the 68 tasks) with the untrained model's answer lengths $0.60 and $0.57, all lower bounds.
